My AI build playbook, part 1: the model is the easy part

Part one of the playbook I use to build AI systems: the principles behind reliable outputs, and a stack you add to only when a build needs it.

CO Chinomso Okere November 2026 6 min read

On this page

Five layers, and the discipline of using few The principles that make outputs reliable A stack you add to, not start with

The hardest part of building an AI system is almost never the AI. The model call is usually a single API request, and the work that decides whether the system holds up is everything around it.

This is the first part of a series on the playbook I use to build AI systems, and it starts with the shape of the thing: the layers a build can have, and the discipline of using only the ones it needs.

I keep this playbook so that no build has to re-argue the same basic decisions, and so that a coding agent can be pointed at it and stay inside choices I already trust. It is less a tutorial than a set of defaults with reasons attached.

01

#Five layers, and the discipline of using few

Any system I build can be read as up to five layers. The AI layer is the model calls, the intelligence, and in practice it is the easiest of the five: often one API call. The backend is the engine that ties everything together and runs the logic. Storage is where data persists. The frontend is the visual layer, and it exists only when a person needs to click something. Infrastructure is where it all runs and how it ships.

The point of naming them is to stand up only the ones a given build actually needs. A classification script is the AI layer in a single Python file, with no backend, no storage and no screen. A client-facing assistant might genuinely need all five. Most early builds use two or three.

A good answer from the model is cheap to produce and expensive to trust.

Calling the model layer the easy one is not a dismissal of the model. It is a statement about where the difficulty actually lives. Trust is built in the layers around it.

02

#The principles that make outputs reliable

A model that returns free text is hard to build on, because the next step has to guess at what it got. So I force the model to return data in a fixed, typed shape rather than prose. In Python that means Pydantic, and it is the backbone of the whole method: predictable outputs, a next step that can rely on them, and a shape you can evaluate against.

structured_output.py
from pydantic import BaseModel class Classification(BaseModel):    label: str    confidence: float    reason: str

The second principle is to use deterministic code wherever it will do the job, and reserve the model for genuine language or judgement tasks. A model call is powerful, but it is non-deterministic and it costs money. A lookup, a rule or a calculation is none of those things, so it stays in plain code.

Third, I store facts and compute what is derived. I persist the inputs and the snapshots: what the model returned, and which settings were in force when it did. Anything derived from those, a flag or a score or a status, is computed when it is read, not written to the record.

03

#A stack you add to, not start with

The tools matter less than the order in which you reach for them. I keep a default choice for each layer, and a note on when to add it and when to leave it alone. Grouped by that question, the stack looks like this.

From day one, every build gets Python as the single backend language, uv to manage the version, packages and virtual environment in one tool, and Pydantic the moment there is any structured data. These are cheap to add and expensive to retrofit, so they go in at the start.

None of this is exotic, and that is the point. The reliability of an AI system comes from unglamorous decisions made early: a typed output instead of a string, a rule instead of a model call, a stored fact instead of a stored guess.
